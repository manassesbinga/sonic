================================================================================
          CHANNELWORKERS (NETFN) - DOCUMENTO DE CONTEXTO CONSOLIDADO
                         (VERSÃO CORRIGIDA v2.0)
================================================================================

Este documento consolida toda a análise estrutural, decisões arquiteturais,
soluções técnicas e diagramas gerados para a criação do ChannelWorkers:
um motor open-source e auto-hospedado para executar funções escritas em
JavaScript/WASM diretamente no canal de transmissão de rede (In-Channel),
sem alterar o cliente, o servidor ou configurações de balanceadores de carga.

================================================================================
1. O CONCEITO E A DIFERENÇA DE OUTROS PROJETOS (POR QUE É ÚNICO?)
================================================================================

Atualmente no GitHub e no mercado existem três grandes grupos de ferramentas,
mas nenhuma resolve o problema de rodar lógica invisível no canal:

*   Runtimes de Borda (Ex: cloudflare/workerd): São apenas servidores web.
    Eles NÃO interceptam tráfego na rede de forma transparente. Você precisa
    alterar seu DNS, redirecionar o tráfego ativamente ou mudar o código
    dos microsserviços para usá-los.
*   Plataformas FaaS (Ex: OpenFaaS, Knative): Projetadas para subir containers.
    Possuem overhead de rede gigantesco (API Gateway, roteamento L7, etc.).
    Não servem para interceptação em tempo real no canal a taxas de 10Gbps+.
*   Sistemas eBPF de Baixo Nível (Ex: eunomia-bpf): Permitem rodar código no
    Kernel, mas exigem C/Rust, conhecimento profundo de syscalls e restrições
    severas de memória. Não há abstração de alto nível (L7) para desenvolvedores.

O ChannelWorkers é único porque permite escrever funções JavaScript de alto
nível (onTraffic) que são implantadas automaticamente na rede (Kernel/Socket)
via eBPF, oferecendo acoplamento zero e performance próxima do metal.

================================================================================
2. SOLUÇÃO DE DESAFIOS CRÍTICOS E EVITAÇÃO DE ERROS DE ARQUITETURA
================================================================================

Para garantir a viabilidade prática do produto em ambientes de produção (VPS),
corrigimos os seguintes erros de lógica e lacunas de design:

--------------------------------------------------------------------------------
A. HTTPS no Canal de Trânsito (Uprobes vs MITM)
--------------------------------------------------------------------------------
*   Erro Comum: Achar que eBPF Uprobes (que leem chaves SSL em memória) podem ser
    usados em roteadores ou gateways de trânsito. Uprobes exigem rodar na mesma
    máquina física que o processo criptográfico.
*   Solução do ChannelWorkers: Em nós de rede de trânsito (VPS/Gateway), a
    interceptação HTTPS é feita obrigatoriamente por Terminação TLS (Proxy MITM)
    com geração de certificados on-the-fly assinados por uma CA Raiz local.

--------------------------------------------------------------------------------
B. Bypass de Kernel (AF_XDP) vs Complexidade do TCP
--------------------------------------------------------------------------------
*   Erro Comum: Fazer bypass do Kernel com AF_XDP para todo o tráfego TCP. Isso
    obriga a reconstruir uma pilha inteira de TCP (handshakes, retransmissões) em
    espaço de usuário, aumentando a chance de bugs e atrasos.
*   Solução do ChannelWorkers: Usar eBPF Sockmap em conjunto com TPROXY. O Kernel
    Linux faz a montagem robusta dos pacotes TCP e o eBPF Sockmap desvia o
    stream TCP limpo e linearizado diretamente para o motor em Go em microssegundos.

--------------------------------------------------------------------------------
C. Latência, Consultas a Bancos de Dados e Loops de CPU
--------------------------------------------------------------------------------
*   E/S Não-Bloqueante: O motor em Go processa as conexões em Goroutines. Chamadas
    assíncronas (como queries em bancos ou APIs de IA) apenas pausam a goroutine
    específica, mantendo a CPU livre para outros pacotes.
*   TCP Backpressure: Se o banco de dados demorar, a janela TCP de recepção
    do cliente diminui automaticamente. O cliente envia dados mais devagar,
    impedindo descarte de pacotes (packet drops).
*   Watchdog de CPU: Um timer interrompe a VM JavaScript se a função do usuário
    executar por mais de 50ms, disparando um modo failsafe (Bypass ou Bloqueio).

--------------------------------------------------------------------------------
D. [CORRIGIDO] Thread-Safety da VM JavaScript (Goja)
--------------------------------------------------------------------------------
*   Problema Identificado: O runtime Goja (goja.Runtime) NÃO é thread-safe.
    Uma única instância de VM NÃO pode ser partilhada entre Goroutines
    concorrentes. Fazê-lo causa data races silenciosos que corrompem o estado
    da VM e geram crashes aleatórios em produção.
*   Solução Implementada: Pool de VMs (sync.Pool)
    O motor Go mantém um pool de instâncias Goja pré-inicializadas usando
    sync.Pool. Cada Goroutine (conexão TCP) pede emprestada uma VM do pool,
    executa a função onTraffic(), e devolve ao pool.
    O código JavaScript do utilizador é compilado UMA ÚNICA VEZ usando
    goja.Compile() e o programa compilado (*goja.Program) é reutilizado em
    todas as VMs do pool, eliminando o custo de re-parsing.
*   Prevenção de Poluição de Estado: As funções do utilizador devem ser
    funções puras (sem estado global). O motor limpa o namespace global da VM
    entre execuções para evitar que variáveis de uma conexão vazem para outra.
*   Padrão de código:

    var compiledProgram, _ = goja.Compile("worker.js", userCode, false)

    var vmPool = sync.Pool{
        New: func() interface{} {
            vm := goja.New()
            vm.RunProgram(compiledProgram)
            return vm
        },
    }

    func handleConnection(conn net.Conn) {
        vm := vmPool.Get().(*goja.Runtime)
        defer vmPool.Put(vm)
        // VM isolada — segura para uso nesta goroutine
    }

--------------------------------------------------------------------------------
E. [CORRIGIDO] Estabilidade do Kernel e Fallback do Sockmap
--------------------------------------------------------------------------------
*   Problema Identificado: O subsistema eBPF Sockmap possui CVEs activas
    (ex: CVE-2025-39913, CVE-2025-38154 — Use-After-Free no
    tcp_bpf_send_verdict). Estas vulnerabilidades podem causar crash do
    Kernel da VPS inteira em produção.
*   Versão Mínima de Kernel Definida:
    - Mínimo Absoluto: Linux 6.1 LTS (com último ponto de release estável)
    - Recomendado: Linux 6.6 LTS (com último ponto de release estável)
    - O daemon DEVE verificar a versão do Kernel no arranque e recusar
      iniciar em versões anteriores a 5.15.
*   Hardening Obrigatório do Kernel:
    - Definir kernel.unprivileged_bpf_disabled = 1 no sysctl para impedir
      que utilizadores não-privilegiados carreguem programas eBPF.
*   Mecanismo de Fallback Automático:
    Se o Sockmap não estiver disponível (Kernel antigo, sem CAP_BPF, ou
    falha ao carregar o programa eBPF), o daemon degrada automaticamente
    para um proxy TCP transparente puro em user-space usando:
        net.Listener (Go) + io.Copy (bidireccional)
    Este modo é mais lento (~30% mais latência) mas garante que o sistema
    NUNCA falha completamente. O utilizador é avisado via log:
        [WARN] Sockmap indisponível. Modo fallback TCP activado.
*   Monitorização Contínua:
    O daemon monitoriza dmesg/syslog em busca de mensagens WARN ou BUG
    relacionadas com BPF ou networking. Se detectar instabilidade, activa
    o fallback automaticamente e alerta o utilizador.

--------------------------------------------------------------------------------
F. [CORRIGIDO] Certificate Pinning e Passthrough de Domínios
--------------------------------------------------------------------------------
*   Problema Identificado: Aplicações móveis (iOS/Android) e SDKs de API
    (Stripe, AWS SDK, apps bancários) usam Certificate Pinning a nível de
    aplicação. Estas apps ignoram a trust store do sistema operacional e
    verificam o hash exacto do certificado do servidor real. O MITM do
    ChannelWorkers será rejeitado silenciosamente, quebrando a conexão.
*   Solução Implementada: Passthrough Automático e Configurável
    1. Detecção Automática: Se o handshake TLS com o cliente falhar (porque
       o cliente rejeitou o certificado MITM gerado), o motor marca
       automaticamente aquele domínio como "pinned" e entra em modo
       passthrough transparente para todas as conexões futuras ao mesmo
       domínio. Neste modo, os bytes crus são encaminhados sem
       descriptografia — a função JS NÃO é executada nesse tráfego.
    2. Lista de Bypass Configurável: O utilizador pode pré-definir domínios
       que nunca devem ser interceptados no ficheiro de configuração:

       # channelworkers.yaml
       bypass_domains:
         - "*.stripe.com"
         - "*.amazonaws.com"
         - "*.apple.com"
         - "banking-app.example.com"

    3. Modo Passthrough Total: Para cenários de depuração onde o
       utilizador quer que o canal funcione apenas como observador de
       metadados (SNI, IP, porta) sem tocar no payload:

       channelw start --passthrough-all

4. PLANO DE BENCHMARK E VALIDAÇÃO (STRESS TEST) — ALVOS REALISTAS
================================================================================

Para validar a viabilidade do produto na VPS, aplicaremos testes separados
por protocolo para evitar alvos irrealistas:

CENÁRIO A: HTTP PURO (sem TLS)
    Ferramenta: wrk ou autocannon (máquina externa)
    Alvo: > 50.000 RPS com função de canal JS activada
    Justificativa: Sem overhead de criptografia, o Sockmap + Goja Pool
    consegue processar dezenas de milhares de requests por segundo.

CENÁRIO B: HTTPS COM MITM TLS
    Ferramenta: wrk com configuração TLS ou k6
    Alvo: 5.000 - 15.000 RPS numa VPS de 4 cores
    Justificativa: O handshake TLS 1.3 (ECDHE + AES-GCM) consome ciclos
    significativos de CPU. Proxies MITM maduros (mitmproxy) atingem
    2.000-5.000 RPS em hardware modesto. O ChannelWorkers, por usar Go
    nativo (crypto/tls) em vez de Python, deve superar esse limite.

CENÁRIO C: LATÊNCIA DE CAUDA (p50/p95/p99)
    Medir a diferença de latência:
    - Conexão directa (Cliente --> Servidor): baseline
    - Conexão via canal (Cliente --> ChannelWorkers --> Servidor): medição
    Alvo: Overhead máximo de 1.5ms no p50 e estável no p99.

CENÁRIO D: CONEXÕES POR SEGUNDO (TCP Churn/CPS)
    Ferramenta: wrk com Connection: close
    Objectivo: Stress na criação/destruição rápida de sockets no Sockmap.
    Monitorizar: vazamento de entradas no BPF Map (bpftool map dump).

CENÁRIO E: LONGEVIDADE (Soak Test — Detecção de Memory Leaks)
    Carga: 5.000 RPS durante 48 horas contínuas
    Monitorizar: RSS de memória RAM do daemon Go + contagem de VMs no pool
    Alvo: Curva de RAM deve estabilizar (platô) após warmup inicial.

CENÁRIO F: BACKPRESSURE TCP (I/O Lento)
    Função JS com delay de 2 segundos (simulando query lenta)
    Carga: 10.000 requisições simultâneas
    Monitorizar: netstat -s para verificar zero packet drops
    Verificar: janela TCP diminui progressivamente (backpressure funcional)

5. CONFIGURAÇÃO DE SEGURANÇA (RODANDO SEM ROOT COMPLETO)
================================================================================

Para evitar rodar o daemon principal como root (UID 0) na VPS, utilizamos
Linux Capabilities adicionadas ao binário compilado:

    sudo setcap cap_bpf,cap_net_admin,cap_sys_resource=ep ./channeld

Hardening adicional obrigatório no sysctl:

    sysctl -w kernel.unprivileged_bpf_disabled=1

Isso concede apenas os poderes necessários para carregar o eBPF, manipular
interfaces de rede e alocar mapas de socket na memória bloqueada, mantendo o
restante do sistema protegido contra vulnerabilidades de código de utilizador.

Versão Mínima de Kernel Suportada:
    Mínimo Absoluto: Linux 6.1 LTS (último patch estável)
    Recomendado:     Linux 6.6 LTS (último patch estável)
    O daemon verifica a versão no arranque e recusa iniciar em < 5.15.

6. DESIGN DO CLI E EXPERIÊNCIA DO PROGRAMADOR (DX)
================================================================================

Para garantir adopção pela comunidade open-source, o CLI do ChannelWorkers
deve oferecer uma experiência de "Time to Hello World" inferior a 5 minutos.

--------------------------------------------------------------------------------
A. INSTALAÇÃO
--------------------------------------------------------------------------------
    # Linux (binário pré-compilado)
    curl -sSL https://channelworkers.dev/install.sh | bash

    # Go (go install)
    go install github.com/channelworkers/channelw@latest

    # Homebrew (macOS/Linux)
    brew install channelworkers/tap/channelw

--------------------------------------------------------------------------------
B. COMANDOS DO CLI
--------------------------------------------------------------------------------
    channelw init                 Cria um novo projecto com estrutura padrão
    channelw new <nome>           Cria uma nova função de canal (gera .js)
    channelw dev                  Inicia o motor em modo desenvolvimento
                                  (hot-reload automático ao salvar ficheiros)
    channelw deploy <ficheiro>    Carrega uma função no daemon de produção
    channelw logs --follow        Mostra logs em tempo real do tráfego
    channelw status               Mostra conexões activas e métricas
    channelw bypass add <domínio> Adiciona domínio à lista de passthrough
    channelw ca install           Instala o certificado CA raiz no sistema
    channelw ca export            Exporta o certificado para uso em outros
                                  dispositivos da rede

--------------------------------------------------------------------------------
C. ESTRUTURA DE UM PROJECTO
--------------------------------------------------------------------------------
    my-channel-project/
    ├── channelworkers.yaml       # Configuração (portas, bypass, limites)
    ├── functions/
    │   ├── auth-injector.js      # Função que injeta token de auth
    │   └── rate-limiter.js       # Função que limita requests por IP
    └── certs/                    # CA raiz gerada automaticamente
        ├── ca.pem
        └── ca-key.pem

--------------------------------------------------------------------------------
D. FORMATO DO FICHEIRO DE CONFIGURAÇÃO (YAML)
--------------------------------------------------------------------------------
    # channelworkers.yaml
    listen_port: 8443
    target_ports: [80, 443, 8080]
    mode: "intercept"              # intercept | passthrough-all | observe

    tls:
      ca_dir: "./certs"
      auto_generate: true

    runtime:
      timeout_ms: 50               # Watchdog de CPU (máx 50ms por execução)
      pool_size: 64                 # Número inicial de VMs Goja no pool
      failsafe: "bypass"           # bypass | block

    bypass_domains:
      - "*.stripe.com"
      - "*.amazonaws.com"
      - "*.apple.com"

    logging:
      level: "info"                # debug | info | warn | error
      format: "json"               # json | text

--------------------------------------------------------------------------------
E. HOT-RELOAD EM DESENVOLVIMENTO
--------------------------------------------------------------------------------
    O comando "channelw dev" inicia um file watcher (fsnotify) que monitoriza
    o directório functions/. Ao detectar alterações num ficheiro .js:
    1. Recompila o programa Goja (goja.Compile)
    2. Invalida todas as VMs do sync.Pool (forçando recriação com novo código)
    3. Conexões activas continuam com o código antigo até terminarem
    4. Novas conexões usam o código actualizado imediatamente
    Nenhuma conexão é perdida durante o hot-reload.

--------------------------------------------------------------------------------
F. EXEMPLO MÍNIMO DE FUNÇÃO DE CANAL
--------------------------------------------------------------------------------
    // functions/hello.js

    function onTraffic(request) {
        // Executado no canal — antes de chegar ao servidor
        console.log("Interceptado:", request.method, request.url);
        request.headers["X-Channel-Worker"] = "Active";
        request.headers["X-Request-Time"] = Date.now().toString();
        return request;
    }

    function onResponse(response) {
        // Executado no canal — antes de chegar ao cliente
        response.headers["X-Processed-By"] = "ChannelWorkers";
        return response;
    }
